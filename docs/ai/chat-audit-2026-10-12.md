## Architecture and factual answers

- `chat-launcher.tsx` mounts under the existing I18n provider and survives route navigation. `chat-panel.tsx` and order code load on demand. No unrelated page was restyled.
- `/api/ai/chat` reuses `aiEnv`, Workers AI, the existing model, challenge/Turnstile gate, rate limiter and global Durable Object budget. Photo and chat attempts share the existing cap of 200; caps were not increased.
- The model produces only a strict intent/search-plan schema. It never generates user-facing prices, products, stock claims, dates, order facts, links, SQL or actions. Authored responses are localized in all seven configured languages. This intentionally bounds the conversation; it is not an unrestricted generative support agent.
- Search uses the existing multilingual catalogue `suggest` and compliance-filtered `listProducts`. Catalogue/store suggestions are labelled discovery, never inventory. Approved live marketplace records may supply offer prices; absent data stays absent. Two-query comparison displays actual matches and missing-data notices.
- Shipping guidance describes the existing service and opens the unchanged calculator. Exact estimates still use the existing weight/dimension/destination form and pricing source.
- Product URLs go through the existing HTTPS/provider allowlist and canonical parser, then the existing official-provider adapter. User URLs are never arbitrary fetch targets. Current providers return no live details, so the assistant does not claim a verified price or availability.
- `chatOrder` uses `phoneOrAuthMiddleware` and `requestDetail(context.userId, ref)`, preserving owner/approved-staff permission checks and indistinguishable missing/foreign references. Only reference/status/events are returned; contacts, attachments and quote amounts are excluded. The model never receives order results, references or URL turns from conversation history.
- Sensitive mutations are unavailable to the model. Purchase/quote/cancellation/account decisions remain in existing authorized pages with their existing confirmation controls.
- Conversation history exists only in component memory: no cookies, local/session storage, database writes or transcript logs. Closing drops loaded private order events. Phone sign-out clears history/consent and cancels in-flight work; Better Auth sign-out reloads the page.

## Security and resource limits

Full-origin checking includes scheme and rejects cross-site requests. Input is strict JSON with consent, a known locale, at most eight history entries, 2000 characters per message and 6000 characters total context; body reads cap at 24 KB. Model output is validated before any source read. Bundled and existing DB compliance filters check every user turn and generated query. No dynamic tool name or arbitrary endpoint can execute.

Inference uses at most 250 completion tokens and the existing 25-second timeout. Gate, body and source reads have deadlines; the browser has a 40-second total deadline and Stop control. Stream decoding is UTF-8 aware and capped at 64 KB. SSE carries progress and validated results, not unvalidated model tokens. Client cancellation prevents subsequent source reads; the binding offers no cancellation guarantee for an already-started inference, so its attempt remains charged. Failure does not refund shared global provider attempts. Chat rate/storage failures fail closed.

Shared Turnstile client cleanup removes widgets/listeners after completion or abort and has a bounded timeout. It preserves the existing `gateFields()` call signature for the photo and other forms. Production currently uses the existing signed challenge fallback; a configured interactive Turnstile challenge still needs deployment-specific browser verification.
